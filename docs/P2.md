# Mango3S P2 reference

This document covers P2's advanced features: compare and sync, SQL migration, reschema, data
masking, scheduled tasks, AI-assisted queries and the MCP server. It describes how each
behaves, how it protects your data and credentials, how to configure it, and what it does
not support.

Each feature is a separate Go package with its own unit tests. The packages talk to MongoDB
through the same session, job and error infrastructure as P0/P1. `internal/api/p2.go` is a
thin layer that binds them to the UI.

| Package | Responsibility |
|---|---|
| `internal/compare` | Collection and database comparison, normalized document hashing, field-level diffs |
| `internal/syncer` | Sync plans built from a comparison; preview → confirm → apply → verify |
| `internal/plans` | Single-use, expiring (30 min) previews shared by sync, transforms and AI writes |
| `internal/backup` | NDJSON before-images of every changed document, and restore |
| `internal/docpath` | Dotted-path get/set/delete, including inside arrays of documents |
| `internal/reschema` | Rename, remove, set, copy, convert, flatten and nest operations (pure functions) |
| `internal/masking` | Masking methods and rule sets (`masking.json`) |
| `internal/transform` | Runs reschema or masking as a dry run, a copy, or in place, then validates the result |
| `internal/migrate` | PostgreSQL / MySQL / SQLite introspection, mapping, copy, embedding, validation, rollback |
| `internal/scheduler` | Approved tasks, cron/interval schedules, retries, misfire handling, run history |
| `internal/ai` | Natural language → validated query proposals (Anthropic Claude), gated writes |
| `internal/mcpserver` | Deny-by-default MCP server (`mango3s mcp`) |
| `internal/mongox/privileges.go` | Least-privilege checks (`connectionStatus` with `showPrivileges`) before writes |

## Data-integrity model

Every operation that changes data follows the same pattern:

1. **Dry run first.** Sync, reschema, masking and AI writes produce a preview: counts, sample
   before/after documents and a list of what would change. Nothing is written.
2. **Explicit confirmation.** Applying a preview needs its single-use plan ID. Destructive steps
   also need you to type the target name (`db.collection`), both in the UI and on the server.
   Plans expire after 30 minutes and can be used only once.
3. **Privilege check.** Before writing, Mango3S checks the session's read-only flag. It then asks
   the server (`connectionStatus` + `showPrivileges`) whether the user has the needed actions on
   that namespace. Missing privileges are reported up front instead of partway through.
4. **Backup.** Before a document is replaced or deleted, its exact current version (canonical
   Extended JSON) is appended to `<config dir>/backups/*.ndjson` (mode 0600) and fsynced. The
   file is written before the change.
5. **Optimistic writes.** Each write is filtered on the full document seen at preview time
   (`$expr: {$eq: ["$$ROOT", {$literal: <doc>}]}`). If another client changed the document after
   the preview, it is **skipped and reported**, never overwritten.
6. **Validation after the write.** Sync re-compares source and target. Transforms re-read the
   output and check counts, `_id` preservation and that the operations no longer apply. Migrations
   compare row counts and 50 sampled rows per table with the source.
7. **Recovery.** Library → Backups lists every backup. Restore puts back replaced and deleted
   documents and removes inserted ones. It is idempotent, so it can be run again after an
   interruption. Migrations roll back from the Migrate tab: collections created by the run are
   dropped, and pre-existing empty targets are emptied.

## Compare and sync

- **Compare** works on two collections or two databases, on the same connection or different
  ones. Options:
  - an optional filter applied to both sides;
  - ignored fields (dotted paths), for example `updatedAt`;
  - field-order-insensitive matching.
- Documents are matched by `_id`. Each side is hashed after normalization. The result has counts
  (identical / changed / only in source / only in target), field-level diffs for a sample, and a
  **fingerprint** of the whole comparison.
- The fingerprint does not depend on read order, so running the same comparison on unchanged
  data gives the same fingerprint. The integration suite checks this (`TestCompareIsRepeatable`).
- Database compare lists per-collection counts and index differences, and can deep-compare each
  collection.
- **Sync** builds a plan from the comparison. Inserting and replacing are on by default; deleting
  from the target is off by default and needs the target typed to confirm. During apply:
  - every document's hash is re-checked against the preview;
  - documents that drifted are skipped;
  - the outcome reports `planned` / `applied` / `skipped`, `matchesPreview` and `verifiedEqual`;
  - `matchesPreview` is true only when exactly the previewed changes were applied.
- Limit: 5 million documents per side.

## Reschema and masking

- **Reschema operations:**
  - `rename`, `remove`, `copy`
  - `set` (shell-syntax value, optionally only if missing)
  - `convert` (to string, int, long, double, decimal, bool, date or objectId)
  - `flatten` (sub-document to `parent_child` fields)
  - `nest` (fields into a sub-document)
  - `_id` cannot be changed.
- **Masking methods:**

  | Method | Effect | Deterministic |
  |---|---|---|
  | `redact` | `"[REDACTED]"` | yes |
  | `partial` | keep the last N characters (`keepLast`, `maskChar`) | yes |
  | `hash` | keyed HMAC-SHA-256 hex | yes |
  | `email` | `u_<hash>@<original domain>` | yes |
  | `randomize` | same length and character classes | yes |
  | `dateShift` | ± up to `maxDays` | yes |
  | `noise` | ± `percent`, numeric type kept | yes |
  | `null`, `remove`, `constant` | as named | yes |

  Each rule's `onUnsupported` (`error` default, `null`, `skip`) decides what happens when a value
  has the wrong type. Deterministic methods are keyed by a random 32-byte key kept in the OS
  credential store (`mango3s:masking-key`). Masked values are therefore stable across runs, so
  joins between masked collections still work, but they can't be reversed or recomputed without
  the key.
- **Modes:**
  - **Dry run** processes up to 100,000 documents.
  - **Copy** writes to a new or empty collection; the source is untouched. This is the
    recommended mode for masking.
  - **In place** is backed up and optimistic like sync, and needs the collection name typed to
    confirm.
- The integration test `TestReschemaAndMaskingIntegrity` checks:
  - every `_id` and document count is preserved;
  - no original sensitive value appears anywhere in the masked copy's bytes;
  - an in-place transform restores exactly from its backup.

## Migration from relational databases

- **Sources:**
  - PostgreSQL (pgx)
  - MySQL / MariaDB (go-sql-driver)
  - SQLite (pure Go; the file is opened `mode=ro`)
- All reads happen inside one read-only `REPEATABLE READ` transaction, so the copy is a
  consistent snapshot.
- **Least privilege:** a `SELECT`-only user is enough. PostgreSQL keys are read from
  `pg_catalog`, which works for users that can't see `information_schema` constraints. The compose
  file creates such users: `mango_reader` / `reader`.
- **Mapping:** one table to one collection. You pick field names and target types; Mango3S
  suggests types from the column types. `_id` can be:
  - the primary key (`pk`); a composite key becomes a sub-document;
  - a new ObjectId (`objectId`).

  Child rows can be **embedded** into their parent as an array through a single-column foreign
  key. The embedded-row total is checked against a SQL `JOIN` count.
- **Safety:** target collections must be new or empty. Every run is recorded in `migrations.json`
  with a per-table report and the validation result, and can be rolled back.
- **DSNs** are entered in a password field, used for that one run, and **never stored or logged**.
  Run history shows a host/database hint with credentials removed.
- See [`config/sample-migration.json`](../config/sample-migration.json) for a request matching
  the seeded `docker/sql-init` schema.

## Scheduled tasks

| Task type | What it does |
|---|---|
| `export` | P1 export of a query to JSON/CSV; `{date}` and `{time}` in the path are expanded |
| `compare` | Compare two collections; the run **fails** when they differ, so it shows up in history |
| `sync` | Compare + apply the sync plan (backed up, drift-safe, verified) |
| `maskCopy` | Masked copy into a target collection, optionally replacing the previous copy |

Only these registered types can run; there is no arbitrary command or script task.

### Policies

- **Approval:**
  - A new or edited task can't run until you approve it. Approval shows the exact parameters.
  - Approval is bound to a SHA-256 of the task type and parameters. Changing either, including by
    editing `tasks.json` by hand, revokes it.
  - Saving never approves.
- **When it runs:** only while Mango3S is open and the scheduler is enabled (Settings →
  Scheduler). The scheduler checks every 30 seconds. Schedules use 5-field cron
  (`minute hour day month weekday`, local time) or an interval of 1 minute to 31 days.
- **Overlap:** if the previous run of the same task is still going, the new run is skipped and
  recorded as `skipped`.
- **Failure:** a failed attempt is retried up to `maxAttempts` (1–10) times. The wait starts at
  `backoffSeconds` and doubles each attempt. Every attempt's error is kept in the run record. A
  run that exhausts its attempts is `failed`, and the task stays scheduled.
- **Restart:**
  - Runs that were in progress when the app stopped are marked `interrupted` at the next start.
  - Runs missed while the app was closed are handled by the task's misfire policy:
    - `skip` (default) writes one `missed` record and moves to the next time;
    - `runOnce` runs once at startup.
  - Never more than one catch-up run.
- **History:** `task_runs.json` keeps the last 500 runs (state, trigger, attempts, errors, result
  summary, job ID). Live progress is in the Jobs panel.

See [`config/sample-tasks.json`](../config/sample-tasks.json) for one task of each kind. Tasks
loaded from a hand-edited file start unapproved.

## AI-assisted queries and pipelines

- **Providers** (Settings → AI). Settings detects which ones are available on this computer,
  without sending anything to a model:

  | Provider | How it runs | Sign-in / billing |
  |---|---|---|
  | Anthropic API (default) | Official Go SDK, structured JSON output; model configurable (default `claude-opus-5-5`) | API key, billed per use |
  | Claude Code | The installed `claude` CLI: `-p --output-format json --json-schema …` with **all tools disabled** (`--tools ""`), no MCP servers, no settings or hooks, no saved session, in an empty folder | Your Claude Code sign-in; usage counts against your Claude plan |
  | Codex | The installed `codex exec` in its read-only sandbox with `--output-schema`, `--ephemeral`, in an empty folder | Your Codex sign-in. Codex is an agent and can still read files, so prefer the other providers for untrusted databases. Built from Codex's docs; not run on the development machine |
  | Local model | Ollama's API (`/api/chat` with a JSON schema) or any OpenAI-compatible server: LM Studio, llama.cpp, vLLM, Jan (`/v1/chat/completions`, `json_schema`, falling back to `json_object`) | None. Nothing leaves the computer unless the URL points elsewhere, which Settings warns about. An optional API key goes to the credential store (`mango3s:ai:local`) |

- **Choosing a provider:** Settings shows each provider's status (installed, signed in, models
  available), and a **Test** button sends one tiny request. Answers from every provider go
  through the same JSON extraction and validation. The AI timeout (default 180 s) is separate from
  the query timeout, because local models and CLIs can be slow.
- **Off by default.** Enable it in Settings → AI and add an API key. The key is stored in the OS
  credential store (`mango3s:ai:anthropic`); alternatively set `ANTHROPIC_API_KEY`. The key is
  never sent to the UI or written to logs.
- **What is sent:** your prompt, the `db.collection` name, and field paths with their types and
  presence from a 200-document sample.
  - Optionally, when enabled in Settings and ticked per request, 3 **masked** sample documents:
    values are scrambled, field names and types are kept.
  - Connection strings, hosts, user names, passwords and unmasked values are never sent.
  - "What is sent?" in the dialog shows the exact context before you generate.
- **Validation before you see it:** each proposal is:
  1. parsed with the same MQL parser as the editors;
  2. checked for write stages and operators;
  3. checked against the request's write permission and the connection's read-only flag;
  4. validated by the server with `explain` (`queryPlanner`, nothing executed).

  Proposals that fail validation can't be loaded into an editor.
- **Reads** are loaded into the query or aggregation editor; you run them yourself.
- **Writes** (`updateMany` / `deleteMany`) are offered only when you tick "Allow write proposals".
  1. "Review write" counts the affected documents.
  2. Executing needs the target typed to confirm, a writable session and the server privilege.
  3. The changed documents are backed up first.

  Pipelines with `$out` / `$merge` are never executed from the AI dialog.

## MCP server

`mango3s mcp` runs a Model Context Protocol server over stdio. It uses the same config directory,
connection profiles and credential store as the desktop app, so MCP clients never see
credentials. Configure it in Settings → MCP server, which also shows the client snippet:

```json
{
  "mcpServers": {
    "mango3s": {
      "command": "/Applications/Mango3S.app/Contents/MacOS/mango3s",
      "args": ["mcp"]
    }
  }
}
```

Add this to `claude_desktop_config.json` (Claude Desktop), or run
`claude mcp add mango3s -- /Applications/Mango3S.app/Contents/MacOS/mango3s mcp` (Claude Code).
The policy is read when the server starts, so restart the client after changing it.

### Access control (deny by default)

| Control | Effect |
|---|---|
| `enabled` | The server refuses to start when false (the default) |
| `profiles` | Connection profile IDs the client may use; others are reported as not shared, before any connection is made |
| `databases` | Glob patterns (`shop`, `analytics_*`, `*`). `admin`, `local`, `config` and `system.*` collections are always refused |
| `tools` | Only listed tools are registered; every call re-checks the policy |
| `allowWrites` | Needed for `insert_one`, `update_many`, `delete_many`. Writes also need a writable profile and server privileges, a non-empty filter, at most `maxWriteDocs` matches, and are backed up |
| `maxDocs` | Result cap for find/aggregate (1–500, default 50) |
| `maskRuleSetId` | Masks every returned document with a rule set before it reaches the client |
| `auditLog` | Logs each call's tool, outcome and duration (not its arguments) |

Always refused: `$where`, `$function`, `$accumulator` (server-side JavaScript), `$out` and
`$merge`. `explain` uses `queryPlanner` and doesn't execute the query. See
[`config/sample-mcp.json`](../config/sample-mcp.json).

## Credentials and sensitive data

- Logs redact URI user info (`scheme://user:pass@`), MySQL DSNs (`user:pass@tcp(`),
  `password=` and `"password":` values.
- SQL DSNs are never stored. MCP audit logs omit arguments. AI requests carry no connection data.
- AI and Anthropic keys, the masking key and connection passwords all live in the OS credential
  store, or in the encrypted file backend where no OS store exists.
- Backups contain real document data. They are written with mode 0600 inside the config directory
  and are never sent anywhere. Delete them from `<config dir>/backups` when they are no longer
  needed.

## Tests

```bash
make test                       # unit tests (Go + frontend)
make mongo-up sql-up            # MongoDB 8, PostgreSQL 17, MySQL 8.4 with seed data
make test-integration-sql       # integration suite incl. PostgreSQL and MySQL migrations
```

| Acceptance criterion | Test |
|---|---|
| Comparisons are repeatable | `TestCompareIsRepeatable`, `compare` unit tests (order independence, normalization) |
| Sync preview matches what is applied | `TestSyncPreviewMatchesApplyAndRestores`, `syncer` tests (drift skipped, single-use plans, delete confirmation) |
| Migration data integrity | `TestMigrationFromSQLite`, `…Postgres`, `…MySQL` (types, embeds, validation, rollback); `migrate` unit tests |
| Masking | `masking` unit tests (every method, determinism, key separation, unsupported values); `TestReschemaAndMaskingIntegrity` |
| Scheduler failure/restart | `scheduler` tests: approval invalidation, overlap, retries with backoff, interrupted runs, misfire skip/runOnce, history cap; `TestScheduledExportThroughAPI` |
| AI operations validated | `ai` tests (parse, write detection, read-only policy, no credentials in prompts); `TestAIProposalsValidatedAndGated`; frontend `p2.test.tsx` (writes need typed confirmation) |
| MCP access control | `mcpserver` tests (tool/profile/database/operator denials before connecting, caps, masking, audit without arguments); `TestMCPAgainstRealServer` |
| P0/P1 unchanged | The full existing unit and integration suites |

## Unsupported capabilities

- **Compare/sync:**
  - Documents are matched by `_id` only; no custom match keys.
  - No three-way merge or conflict resolution; drifted documents are skipped.
  - Index differences are reported but not synced. Validators, views and collection options are
    neither compared nor synced.
  - No change-stream or continuous sync.
  - No more than 5 million documents per side.
- **Migration:**
  - PostgreSQL, MySQL/MariaDB and SQLite only. No SQL Server or Oracle.
  - No views, stored procedures or triggers.
  - Embedding is one level deep, through single-column foreign keys only.
  - No incremental or CDC migration; each run is a full copy into new or empty collections.
  - Column types Mango3S doesn't recognize (for example PostGIS geometry or custom PostgreSQL
    types) default to string.
- **Reschema:**
  - No arbitrary JavaScript or aggregation-expression transforms.
  - No schema validator generation.
  - Array restructuring is limited to paths through arrays of documents.
- **Masking:**
  - No format-preserving encryption and no reversible tokenization.
  - Consistency across separate installations needs the same masking key, and the key can't be
    exported.
- **Scheduler:**
  - Runs only while the desktop app is open; there is no OS service or daemon.
  - Multi-step tasks run their steps in order (up to 20, stop or continue on error); there are no
    dependencies between separate tasks.
  - No calendar exclusions or time zones other than local time.
  - No notifications beyond the in-app history.
- **AI:**
  - Providers are Anthropic Claude, Claude Code, Codex and local models (Ollama or any
    OpenAI-compatible server); no other hosted APIs.
  - One collection per request; no `$lookup` suggestions across collections.
  - No index creation, DDL, or AI-run `$out` / `$merge`.
  - Prompts and responses are not stored.
- **MCP:**
  - stdio transport only; no HTTP/SSE and no remote access.
  - No per-client identities or per-client policies.
  - The policy is read at server start.
  - No index, user or role management tools.
- **General:** no multi-user approval workflow; approvals are local to this machine.
